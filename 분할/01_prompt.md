### LLM Deployment

**개요**

- LLM Inference (추론): 학습된 LLM에 프롬프트를 입력하고 텍스트를 생성하는 일련의 과정
    - Prefill, Decode
- LLM Serving (서빙): 학습된 LLM을 API로 배포하고 클라이언트 요청에 응답을 제공하는 과정
- vLLM: 가상화를 적용한 LLM 서빙 엔진. GPU 메모리 낭비를 줄이고, 여러 요청을 동시 처리하고, 같은 GPU에서 더 많은 응답 생성하기 위함.

**서빙 기초 구조**

- OpenAI Compatible API: OpenAI와 호환하여 사용하는 API 방식
- Streaming Response: 토큰이 생성될 때마다 생성된 조각을 순차적으로 전달하는 응답 방식
- Context Length: 모델이 한 번의 추론에서 처리할 수 있는 입력과 출력 토큰을 합친 최대 토큰 수
- Max Tokens: 생성가능한 최대 출력 토큰 수. 파라미터로 지정
- Memory Usage: 점유되는 메모리 총량
- Structured Outputs: JSON Schema 등 형식에 맞게 생성하도록 강제하는 기능

**추론 최적화**

- KV Cache: LLM 추론 중 이전 토큰의 Key, Value 벡터를 GPU 메모리에 저장한 데이터. 다음 토큰을 생성할 때 재사용하여 중복 Attention 연산을 줄이는 캐시 구조. TC vs SC
- Continuous Batching: 완료된 요청을 즉시 빼고 새 요청을 즉시 넣어 배치를 매 스텝마다 갱신하는 스케줄링 기법. 프롬프트 순서에 영향을 받는지 의문
- Paged Attention: KV Cache를 고정 크기 블록으로 나누어 비연속 GPU 메모리에 저장하고, Attention 계산 시 필요한 블록을 찾아 참조하도록 만든 KV Cache 관리 방식
- Prefix Caching: 여러 요청이 공유하는 프롬프트 앞부분의 KV Cache를 저장해두고, “같은 접두부로 시작하는 다음 요청”에서 재사용해 Prefill 계산을 줄이는 LLM 서빙 최적화 기법. 예시: **시스템 프롬프트** 등
- Throughput: 처리량, LLM 서빙 시스템이 단위 시간 동안 여러 요청을 처리하며 생성한 출력 토큰의 총량
- Latency: 지연 시간, LLM 서빙에서 요청을 보낸 시점부터 첫 토큰이 도착하거나 전체 응답이 완료되기까지 걸리는 시간
- Tensor Parallelism: 하나의 LLM을 여러 GPU에 나누어 올리고, 각 GPU가 모델 연산의 일부를 동시에 처리하도록 하는 병렬화 방식. 안정적으로 동시 요청을 처리하기 위한 방식
- Speculative Decoding: Draft 모델과 Target 모델로 나누어 추측과 검증 작업을 분리하는 추론 가속 기법. 작고 빠른 Draft 모델이 다음 토큰 여러 개를 미리 추측하고, 크고 정확한 Target 모델이 그 토큰들을 한 번에(병렬로) 검증.

**LLM 배포**

- Docker Containerization: 서비스 프로젝트가 의존하는 모든 설정을 하나의 컨테이너 이미지(격리된 공간)으로 묶는 과정. LLM 서빙 애플리케이션과 실행 환경을 컨테이너화 함. 이후 GPU가 할당된 컨테이너로 배포, 실행함.
- Multi-Instance GPU (MIG): *NVIDIA GPU 하나를 자체 연산 자원과 메모리를 가진 여러 개의 독립 GPU 인스턴스로 분할하는 하드웨어 수준 파티셔닝 기술*
- Monitoring: 운영 중인 LLM 서빙 서버의 지표(처리량·지연시간·GPU 메모리·대기 큐)를 지속적으로 수집하고 시각화해 서버 상태를 관측하는 것
